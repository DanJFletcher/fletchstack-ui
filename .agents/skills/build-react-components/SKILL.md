# Build React components with Storybook

For this repository, follow the [component authoring recipe](../../../docs/component-authoring.md) for concern-specific references, mechanical setup, registration, and verification. Reuse established session context; inspect additional setup only when relevant inputs change. The scaffold prepares structure, while API decisions, semantic tokens, meaningful tests, and accessibility review remain authored work.

From the project root, read `.agents/guidelines/component-library.md` and `.agents/guidelines/design-tokens.md` when present. If either is missing, follow this workflow and the project's existing instructions. AGI users can select the companion guidelines separately.

1. **Find the approved pattern.** Locate its purpose, variants, states, and semantic tokens. If the project has no foundation, use `establish-design-system` if available, or ask where the team will record approved patterns and tokens. For a gap, explain the user need, what existing patterns cover, and the missing decision. Get that decision recorded before implementing the missing behavior or styling.
2. **Define the public contract.** State the component's responsibility, supported inputs and states, accessible name, keyboard and focus behavior, and relationships to other controls. Prefer native semantics. Compose existing pieces where they match the pattern. The component owns its internal padding and layout. Its parent owns placement and spacing between siblings. Use semantic tokens for design values and CSS pixels for spatial dimensions. Let text-bearing controls wrap and grow.
3. **Build and exercise observable behavior.** Choose test cadence and evidence under the shared [development policy](../../guidelines/testing-guidelines.md#development-policy). Follow its [execution policy](../../guidelines/testing-guidelines.md#repository-test-execution): use coverage-free development feedback and defer full unit/integration coverage gates until implementation, tests, cleanup and review of the agreed scope are finished. Inspect the Storybook version, framework, and runner before choosing commands. Add stories for meaningful states and at least one representative composition. Use story interactions, such as a `play` function, to act as a user and assert on public outcomes using roles and accessible names where applicable. A journey may take several actions to verify one behavior. Apply unit-test rules within their unit-test scope.
4. **Verify accessibility.** Default to WCAG 2.2 AA. Use the installed runner's supported axe integration, select applicable rules, and confirm violations fail CI. In Storybook setups that support it, set `parameters.a11y.test` to `'error'` and verify the CI runner executes the checks. Check the rendered states after any asynchronous transitions. Manually check keyboard operation and focus, relevant screen-reader behavior, text enlargement to 200%, reflow at a 320 CSS pixel viewport where applicable, and user text-spacing overrides. Record what ran and what remains unverified. [Storybook accessibility testing](https://storybook.js.org/docs/writing-tests/accessibility-testing) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

For an approved Button, verify keyboard activation and its accessible name, then show it with siblings in a ButtonGroup that supplies the gap. If a destructive variant is requested and missing, bring the use case and existing patterns to the design-system owner. Resume that variant once its behavior, states, and token roles are recorded.
